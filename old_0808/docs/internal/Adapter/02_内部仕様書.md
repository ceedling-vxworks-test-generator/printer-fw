# Adapterレイヤ 内部仕様書

対象: `core/adapter`(`AdapterDispatcher`)

本書は、Adapterレイヤの**内部処理ルール**を、実装(C++コード)を読まなくても追えるレベルで記述したものである。
クラス/メソッドの具体的なシグネチャや行番号は `03_詳細設計書.md` を参照。

---

## 1. 処理ルール一覧(`Dispatch(id, value)`)

`Dispatch()`は、以下のルールを**上から順に**適用する。いずれかのルールで処理を打ち切った場合、それ以降の
ルールは評価されず、`StoreInputQueue`への投入も行われない。

### ルール1: DataItem定義の検索

`id`をキーに、コンストラクタで受け取った`ProductDefinition`から`DataItemDefinition`を検索する。

- 見つからない場合 → **処理中断、`false`を返す**。
  (未登録の`RIDataId`。製品定義に存在しないデータ項目は扱えない。)

### ルール2: 型検証

見つかった`DataItemDefinition::rawValueType`と、渡された`value.type`を比較する。

- 一致しない場合 → **処理中断、`false`を返す**。

  このルールが無いと、後続の正規化(`normalize`)が素通し関数(`IdentityNormalize`)の場合に、
  `item.valueType`(=`setValueType`として上書きされる)と実際の`RIMValue::type`が食い違ったまま
  Storeへ積まれてしまう。これは過去に実際に発生した不整合であり、その再発防止のための必須チェックである。

### ルール3: 正規化

`DataItemDefinition::normalize(value, context)`を呼び出し、`value`(rawValueType型)を
`setValueType`型の値へ変換する。

- `context`は現状常に`nullptr`を渡す(単位変換等のコンテキスト機構は未導入)。
- `rawValueType == setValueType`のDataItem(現行の全DataItem定義がこれに該当)では、`normalize`は
  `IdentityNormalize`(入力をそのまま返す)で十分。
- `rawValueType != setValueType`となるDataItemを将来追加する場合は、専用の`normalize`実装
  (例: `NormalizeTemperatureSensorA`のように単位変換を行うもの)を用意する。

### ルール4: RIMDataItemの構築

以下の内容で`RIMDataItem`を構築する。

| フィールド | 値 |
| --- | --- |
| `id` | 引数`id` |
| `valueType` | `definition->setValueType`(正規化後の型を採用。ルール3の出力`RIMValue`が実際にこの型でタグ付けされている前提) |
| `value` | ルール3の出力(正規化後の値) |

### ルール5: Storeレイヤへの投入

構築した`RIMDataItem`を`StoreInputQueue::Push()`で投入し、`true`を返す。

以降の処理(変更検知・永続化・Capability再評価・通知)はStoreレイヤ(`core/store`)以降の責務であり、
Adapterレイヤはここで関与を終える。

## 2. 状態・スレッドモデル

- `AdapterDispatcher`自身は可変な内部状態を持たない(`product_`/`queue_`への参照のみ)。
- `Dispatch()`は呼び出したスレッド上でそのまま同期実行される(専用ワーカースレッドは持たない)。
- 複数スレッドから同時に`Dispatch()`を呼んでも、`StoreInputQueue::Push()`内部の`std::mutex`により
  キューへの投入自体は競合しない。ただし`Dispatch()`の呼び出し自体に順序保証はない
  (複数スレッドが同時に同じ`id`へ書き込んだ場合、Storeレイヤ側での到着順が処理順になる)。

## 3. 依存関係

```
AdapterDispatcher
 ├─ ProductDefinition / DataItemDefinition (products/common, core/common)
 │    └─ FindDataItem() で id → DataItemDefinition を解決
 ├─ RIMValue / ValueType (core/common)
 │    └─ 型検証・正規化の入出力
 ├─ RIMDataItem (core/common)
 │    └─ Storeレイヤへ渡す単位
 └─ StoreInputQueue (core/store)
      └─ 正規化後の値の投入先
```

Adapterレイヤは**製品固有の型名(PrinterA、TemperatureSensorA等)を一切知らない**。すべて
`ProductDefinition`経由の間接参照で完結する(`architecture.md`の「core は製品を知らない」方針に準拠)。

---

## 4. エラー時の挙動まとめ

| 状況 | `Dispatch()`の戻り値 | Storeへの投入 | 呼び出し元(rim_api.cpp)での扱い |
| --- | --- | --- | --- |
| `id`が製品定義に無い | `false` | なし | `RI_INVALID_PARAMETER` |
| `value.type`が`rawValueType`と不一致 | `false` | なし | `RI_INVALID_PARAMETER` |
| 正常系 | `true` | あり(1件) | `RI_SUCCESS` |

`Dispatch()`は例外を送出しない(内部で例外を投げる処理を呼んでいない)。

---

## 5. 既知の制約・未対応事項

- `context`引数(正規化時の補足情報。例: 単位指定)は現状常に`nullptr`固定。将来的に単位変換等を
  行いたい場合は、呼び出し元(rim_api.cpp等)からcontextを受け取れるようAPIを拡張する必要がある。
- ハードウェア起点の実装(`IHardwareAdapter`を実装する具体クラス)は現時点でリポジトリに存在しない。
  そのような実装を追加する場合、ハードウェアの生値(型不定)から`rawValueType`通りの`RIMValue`を
  組み立てる責務は、その実装(Adapter個別実装)側に置く設計とする(`Dispatch()`側では持たない)。
