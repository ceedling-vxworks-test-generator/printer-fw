## 3. 層別 照合・ギャップ表

### 3.1 RIM_AdapterLayer（L1）

| 項目 | drawio | md（仕様書/詳細） | ③整合後のあるべき姿 |
|------|--------|------------------|-------------------|
| 名称 | Data Transform Layer / Adapter | RIM_AdapterLayer | **RIM_AdapterLayer**（別名: Data Transform） |
| 変換規則 | TransformRule(Resolver) | Rule / RuleResolver | **Rule / RuleResolver** |
| 構成 | — | RawDataInput → RuleResolver → Rule → DataStoreSink | 同左（送信先のみ要調整） |
| timestamp | 「付与する」 | 「現状対象外」(§13.5) | **当面は付与しない**（将来拡張として残す）。drawioの「timestamp付与」は削除 |
| 送信先 | — | **DataStoreSink.enqueue(id, Value)**（単一） | **要調整**：③は入口が3種post。→ 4章 GAP-1 |

**GAP-1（重要）**：Adapterは「単一Sink（enqueue）」前提だが、③DataStoreは入口が
`postFaultInput / postOperationReport / postCurrentValueInput` の3種。
③§6.1が「postの種類とIdの分類の一致を確認」と述べる通り、**Adapter側がデータ性質（Fault/Operation/CurrentValue）を判別してpost先を選ぶ**必要がある。
→ Adapter仕様書に「性質分類（Idベース）と3レーン投入」を追記する。

### 3.2 RIM_DatastoreLayer（L2）— 最大の改修対象

| 項目 | ① drawio | ② 詳細(7/3) | ③ 正(7/7) |
|------|---------|------------|-----------|
| 入口 | — | DataStoreSink（単一） | **CentralInputPort**（3種post） |
| 入力保持 | Domain Data Store+14カテゴリ+キュー | 単一 DataStoreQueue | **3レーン**: FaultInputQueue / OperationReportQueue / CurrentValueBuffer |
| 振り分け | データ格納タスク | 単一 DataStoreDispatcher | **3 Dispatcher**（Fault/Operation/CurrentValue） |
| 保存 | 14カテゴリ | 7 Domain Store | **3 Registry** ← **MachineRegistry**が集約 |
| 差分/時刻 | 各メンバ最終更新時刻+変更フラグ | — | CurrentValueBuffer の dirty + Registry.apply。**最終更新時刻の保持要否は未決**（GAP-2） |
| Snapshot | 「除去」 | SnapshotProvider→SystemSnapshot(Full) をPush | **MachineSnapshotReader.capture(request)→MachineSnapshot(部分)** をCapabilityがPull |
| タイミング制御 | — | SnapshotTrigger | **廃止**（Dispatcherが更新時に notifyUpdated） |
| 排他 | Mutex | Store単位 | **domain単位 mutex**（各Registry内） |

**入力性質の定義（③）**：
- **FaultInput**：異常系（Error/Warning）。高優先・FIFO・即時。FaultState（Raised/Cleared/AllCleared/UpdatedHeal/UpdatedActive）で挙動分岐。
- **OperationReport**：動作報告系。順序保証・FIFO（欠落/順序入替不可）。
- **CurrentValue**：最新値系（センサ等）。Idごと上書き・dirty管理・周期取り出し（takeUpdatedValues）。

**GAP-2**：drawioの「各メンバごとの最終更新時刻＋変更フラグ」を③で保持するか。
③はdirty/差分通知で代替しているが、最終更新時刻の外部提供要否（Accessor経由）が未確定。

### 3.3 RIM_CapabilityLayer（L3）

| 項目 | drawio | md（③ 7/7） | 整合後 |
|------|--------|-------------|--------|
| 入力 | Domain Data Storeから取得 | onRegistryUpdated(RegistryDomainSet) → capture | ③に一致（Pull型Snapshot） |
| 構成 | ルール評価＋8 Cap | CapabilityManager / Builder / DiffChecker / PriorityChecker | ③に一致。8 Capは生成対象として明記 |
| Cap一覧 | Error/Job/Env/Maint/Health/Safety/Consumable/Print（8種） | md §4.2〜4.3 が **TBD** | **drawioの8 Capをmdに反映**（TBD解消の入力にする） |
| 差分検知 | （Capability側で変更検知）＋Publisher側でも差分管理 | CapabilityDiffChecker が担当 | **差分検知はCapabilityが担当**。Publisher側①との重複を整理（GAP-3） |
| 派生イベント | Threshold/Event 派生イベント発行 | Error/Job変化時に明示イベント通知（§7） | ③に一致。Thresholdの扱いは下記 |
| Threshold | 「閾値跨ぎ判定はCapability層で行う」（drawio注記） | 記載なし | **Capability層で閾値跨ぎを判定**しイベント化する旨をmdに追記 |
| PrintCap | 「他Capではなく DataStore にのみ依存。Cap合成はFacadeで」 | 記載なし | 設計原則としてmdに明記 |

**GAP-3**：差分管理の所在。drawio Publisher①「State Repository（最終配信値・差分管理）」と
Capability の CapabilityDiffChecker が重複。
→ **意味的差分（Capが変わったか）＝Capability**、**配信的差分（各購読者へ前回何を送ったか）＝Publisher**、と役割分担で切り分ける方針を提案。

### 3.5 RIM_PublisherLayer（配信専用）— **仕様書 未作成**

| 項目 | drawio | md |
|------|--------|-----|
| 構成 | ①State Repository（最終配信値・差分管理）／②Publish Engine（Capごとタスク）／③Subscription Broker（購読管理・配信） | **なし**（Capability仕様に IPublisher.notify のみ） |
| トリガ | OnChange / Periodic / Threshold / Event / Initial（＋Heartbeat=廃止予定） | — |
| 制御 | Rate Limit、関心Cap一致は Publish Dispatcher で判定 | — |
| 前回値 | 「前回値は保持しない（L3が変更項目を知る）」との注記あり ↔ ①名称は「差分管理」 | — |

→ **新規作成対象**。drawioの3分割（State Repository / Publish Engine / Subscription Broker）を基に
「RIM_PublisherLayer仕様設計書.md」を起こす。①の「差分管理」と「前回値を保持しない」注記の矛盾は GAP-4 で解消。

**GAP-4**：Publisher①State Repositoryは「最終配信値」を保持するのか否か。
OnChange/Threshold配信を購読者単位で行うなら**配信済み値の保持が必要**。
drawio注記「前回値保持しない」はCapability層の話（意味的差分）と混線している可能性。
→ **Publisherは購読者ごとの最終配信値のみ保持**、Capの前回値はCapabilityが持つ、で切り分け提案。

## 5. drawio 修正指示一覧（**レイアウトは現状を維持**）

現行drawioの2軸レイアウト（情報軸＝縦のレイヤ帯、駆動軸＝右、外部購読者＝外周）は維持し、
**DataStore帯の中身**と**用語ラベル**のみ差し替える。

1. **DataStore帯を③構造に置換**：
   - `CentralInputPort` → [`FaultInputQueue`／`OperationReportQueue`／`CurrentValueBuffer`] → [`FaultDispatcher`／`OperationDispatcher`／`CurrentValueDispatcher`] → [`FaultRegistry`／`OperationRegistry`／`CurrentValueRegistry`] ← `MachineRegistry`（集約） → `MachineSnapshotReader`
   - 「Domain Data Store / 14カテゴリ / Domain Status Store Snapshot / 山下案」ブロックは撤去
2. **Snapshot経路をPull型に**：Dispatcher …notifyUpdated(domains)…▶ Capability、Capability ─capture(request)▶ MachineSnapshotReader
3. **Adapterラベル**：TransformRule → Rule、TransformRuleResolver → RuleResolver、「timestamp付与」除去、送信先を「性質判別→3種post（CentralInputPort）」に
4. **Capability帯**：8 Cap（Error/Job/Env/Maint/Health/Safety/Consumable/Print）を明示、「閾値跨ぎ判定＝当層」「PrintCapはDataStore依存・合成はFacade」注記を保持
5. **Publisher帯**：①State Repository（配信的差分）／②Publish Engine／③Subscription Broker と5トリガ（OnChange/Periodic/Threshold/Event/Initial）を保持。Heartbeat本体は撤去し外部タスク注記化
6. **凡例**：タスク／イベント／処理の流れ／データを伴う処理の流れ／外部取得、を維持
