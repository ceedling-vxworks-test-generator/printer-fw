システムライフサイクル設計書（全層共通・H-6対応）

本書は、RIM（ReactiveInfoManager・情報軸）全層（L1 RIM_AdapterLayer 〜 L4 RIM_PublisherLayer および隣接 Accessor Layer）の起動・初期評価・停止の順序を定義する。 各層の詳細設計書はライフサイクルに関して本書を正とする。

1. 起動シーケンス

Phase 1: 構築
  1-1. RIM_DatastoreLayer構築（Registry群 / MachineRegistry / Queue / Buffer / Reader / CentralInputPort）
       ※この時点で CentralInputPort は「受付閉鎖」状態
  1-2. RIM_CapabilityLayer構築（Manager / Builder / Diff / Priority、prev=空Set）
  1-3. RIM_PublisherLayer構築（Engine / StateRepository / Broker）
  1-4. Accessor Layer構築（PrinterStatusReader）

Phase 2: 結線・スレッド起動
  2-1. Dispatcher群に IRegistryUpdateNotifier（=CapabilityManager）を登録
  2-2. CapabilityManager に IPublisher（=Publish Engine）を登録
  2-3. Capability専用スレッド起動（pending集合は空・待機状態）
  2-4. Dispatcherスレッド群・CurrentValueDispatcherタイマ起動
  2-5. Publisherタスク群起動

Phase 3: 初期評価（重要）
  3-1. CapabilityManager が全ドメインで初期フル評価を1回実行する
       （capture(AllDomains) → build → prev確立 → 初回 notify(capability) をPublish）
       ※これにより「変化が起きるまで現在Capabilityが存在しない」状態を排除する
  3-2. 初回notifyがStateRepositoryに初期値として届く

Phase 4: 受付開放
  4-1. CentralInputPort 受付開放（Adapter/入力元の投入開始はこれ以降）
  4-2. Subscription Broker の subscribe 受付開放
       （subscribe時のInitial配信は getCurrentCapability() から取得可能：Phase 3で確立済み）

起動時の保証

  • 通知喪失なし：Notifier登録（2-1）は受付開放（4-1）より前であるため、 登録前にDispatcherが通知を発行する状況は構造的に発生しない。
  • Initial配信可能：Phase 3の初期フル評価により、subscribe時点で必ず現在Capabilityが存在する。
  • Phase 4より前の post* は受付閉鎖エラーとして拒否する（呼び出し側は起動完了を待つ）。

2. 停止シーケンス

Phase 1: 入力遮断
  1-1. CentralInputPort 受付閉鎖（以降の post* は拒否）
  1-2. Subscription Broker の新規 subscribe 受付停止

Phase 2: ドレイン
  2-1. FaultInputQueue / OperationReportQueue が空になるまで待機（タイムアウト付き・cfg）
  2-2. CurrentValueDispatcher を1回追加実行して Buffer の残dirtyを反映

Phase 3: スレッド停止（データ流の上流から下流へ）
  3-1. Dispatcher群へ停止要求（stop tokenで dequeue ブロックを解除）→ join
  3-2. Capabilityスレッドへ停止要求（pending処理を完了してから停止）→ join
  3-3. Publisherタスク群へ停止要求（送出中のものは完了を待つ）→ join

Phase 4: 破棄（構築の逆順）
  4-1. Accessor → Publisher → Capability → DataStore の順に破棄
       ※参照する側を先に破棄する（Capability停止後にReaderをcaptureする者はいない）

停止時の保証

  • dequeue() / Capability待機（condition variable）は停止要求で解除可能であること（各詳細設計に明記済み）。
  • 上流から順に止めるため、停止済みコンポーネントへの呼び出しは発生しない。
  • ドレインのタイムアウト超過時は残データ件数をログに記録して停止を続行する （Fault/Operationの残件はログから追跡可能とする）。

3. 各層詳細設計との対応

層 本書が規定する事項 該当詳細設計
DataStore 受付開放/閉鎖、stop token付きdequeue、ドレイン DataStore詳細 §4.1/§5.2
Capability 初期フル評価（起動Phase 3）、停止要求付き待機 Capability詳細 §1.1
Publisher タスク停止、subscribe受付制御 Publisher詳細 §1.1
Accessor 破棄順序（最初に破棄） Accessor詳細
