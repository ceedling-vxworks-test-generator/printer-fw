# RIM 移行計画

現行ツリー(`framework/` `devices/` `capi/`)と構成変更ツリー
(`構成変更/librim/RIManager/`)をどう1本にまとめるかの計画。

すべて **実際にビルド・計測して確認した事実** に基づく。推測の箇所はその旨を明記する。

---

## 1. 結論

**現行ツリーをベースにし、構成変更ツリーからは Capability 層の型消去と
固定容量基盤を移植する。**

逆(構成変更をベースにする)にしない理由は §3 にまとめた。要点だけ言うと、
構成変更ツリーには現行ツリーが既に解決済みの問題が残っている一方、
構成変更ツリーが解決した問題は現行ツリーの1層(Capability)に閉じているため。

---

## 2. 層ごとの現状比較

| 層 | 現行 | 構成変更 | 採用 |
|---|---|---|---|
| Adapter (L1) | `RawValue` / `DataContext` / `IRule` / `IRuleResolver`。単位正規化(摂氏・華氏→ケルビン)、テーブル方式ディスパッチ | センサ種別ごとに1クラス。core が機種 id を参照。コンパイルできないヘッダ4件 | **現行** |
| Datastore (L2) | `CentralInputPort` + 3レジストリ(CurrentValue / Fault / Operation)+ `RegistryDomain`。固定容量 `Queue` | `ValueStore` + `RIMSnapshot` + ワーカ3本 + キュー | **現行**(L2 の構造)<br>+ 構成変更の固定容量基盤 |
| Capability (L3) | `CapabilitySet` に8種の Cap を `framework/` へ直書き。`ICapabilityBuilder` | `CapabilityId` + `CapabilityPayload`(型消去)、`ICapabilityRule`、規則は products 側 | **構成変更** |
| Publisher (L4) | `PublishEngine` / `SubscriptionBroker` / `StateRepository` | `SubscriberMailbox` / `CallbackSubscriptionRegistry`(いずれも固定容量) | 要比較(§5 フェーズ4) |
| コンテナ | `FixedMap` / `FixedVector` / `Queue` / `RingBuffer` | `FixedVector` / `FixedQueue` | 統合(現行に `FixedQueue` を追加) |
| C API | `rim_capi.h` + `rim_ids.h`。単位対応、C 側ミラーとの `static_assert` ドリフト検査、試験3種(smoke/value/perf) | `rim_api.h`(id 引数方式)+ トランポリン枠 | **統合**(§5 フェーズ5) |
| ビルド | install / export / pkg-config / find_package | `-fno-exceptions -fno-rtti` | **両方** |

### 計測値

| 項目 | 現行 | 構成変更(改修前) | 構成変更(改修後) |
|---|---|---|---|
| 定常運転中の動的確保 | 1.0 回/周期 | 3.2 回/周期 | **0 回/周期** |
| 確保箇所 | `CurrentValueBuffer::TakeUpdatedValues()` が `std::vector` を返す 1箇所のみ | Snapshot / ValueStore / キュー3種 / ErrorRepository ほか | なし |

いずれも `operator new` を差し替えて 1000 周期を計測した実測値。

## 3. なぜ現行をベースにするか

### 3.1 構成変更ツリーには現行が解決済みの問題が残っている

- **`RIMDataId` が core にある**(`core/storage/include/RIMDataId.hpp`)。
  現行では既に `devices/printer_a/inc/datastore/RIMDataId.hpp` へ移してあり、
  `framework/` は機種固有 id を **一切参照していない**(grep で確認済み)。
  構成変更ツリーはこの点で退行している。

- **Adapter が機種知識を持つ**。`core/adapter/include/CelsiusTemperatureAdapter.hpp`
  などセンサ種別ごとにクラスがあり、`RIMDataId::TemperatureAbsolute` を直接参照する。
  現行はこれを `IRuleResolver` + テーブル方式に置き換え済みで、
  規則が100〜1000件に増えても core は無改修。

- **単位正規化が無い**。構成変更ツリーは「摂氏用アダプタ」「ケルビン用アダプタ」と
  **型で単位を分けている**。現行は `DataContext::unit` で受けて1つの規則が正規化する
  (同じ id に摂氏でも華氏でも入れられる)。これは仕様で決めた振る舞いなので、
  構成変更の形に戻すと要件を満たさなくなる。

- **死んだヘッダが4件ある**。単体でコンパイルできない:
  `CelsiusTemperatureAdapter.hpp` / `HumidityAdapter.hpp` /
  `KelvinTemperatureAdapter.hpp`(存在しない `SensorData.hpp` を include)、
  `products/skeleton/Pipeline/SkeletonProvider.hpp`(相対パス誤り)。
  どの `.cpp` からも include されていないため今まで気付かれていない。

- **install / packaging が無い**。現行にはある(`rim.lib` として mainFW へ
  組み込むために作った export / pkg-config / find_package 一式)。

### 3.2 構成変更ツリーが解決した問題は1層に閉じている

構成変更ツリーの成果は実質2つで、いずれも移植できる:

1. **Capability の型消去**(`CapabilityId` + `CapabilityPayload`)と
   core/products 分離。現行の `CapabilitySet`(8種を `framework/` に直書き)を
   置き換える対象がはっきりしている。
2. **固定容量基盤**(`FixedVector` / `FixedQueue`)と `-fno-exceptions -fno-rtti`。
   現行には既に `FixedMap` / `FixedVector` / `Queue` / `RingBuffer` があるので、
   足りないのは `FixedQueue` と、`CurrentValueBuffer` の1箇所の修正だけ。

### 3.3 作業量の見積り

| 方向 | 移す対象 | 概算 |
|---|---|---|
| 現行 ← 構成変更(推奨) | Capability 層の置き換え + `FixedQueue` + ビルド指定 | 中 |
| 構成変更 ← 現行 | Adapter 全面作り直し + `RIMDataId` 移設 + install 一式 + 死んだヘッダ掃除 + 実質空のテスト20件の始末 | 大 |

## 4. 決めてほしいこと

計画を確定する前に、判断が要るものが2つある。

### 4.1 スレッドモデル

- **現行**: 単一スレッド。`RIMSystem::Dispatch()` を呼び出し側が回す。
- **構成変更**: ワーカ3本(`DataStoreWorker` / `CapabilityWorker` / `PublisherWorker`)が
  それぞれ独立に動く。

どちらが要件かによって L2/L4 の移植範囲が変わる。VxWorks 上でのタスク割り当てを
呼び出し側(mainFW)が決めたいなら現行、RIM 内部で完結させたいなら構成変更。

**この判断が付くまでフェーズ4以降には着手しない。**

### 4.2 Publisher 層

現行の `PublishEngine` / `SubscriptionBroker` / `StateRepository` と、
構成変更の `SubscriberMailbox` / `CallbackSubscriptionRegistry` は、
どちらも動くが設計が違う(前者は購読者主体、後者は Capability 主体)。
固定容量化は構成変更側が済んでいるが、現行側の機能を落としてよいかは未確認。

## 5. 段階

各フェーズは **単独でビルドが通り、単独でマージできる** 単位に切ってある。
途中で止めても壊れた状態にはならない。

### フェーズ0: 現行ツリーの既知の不具合を先に潰す

構成変更の話と独立に、今分かっている問題を先に片付ける。

- `CurrentValueBuffer::TakeUpdatedValues()` の `std::vector` 返しを、
  呼出側の入れ物へ詰める形へ(現行で唯一の定常確保。1.0回/周期 → 0)
- `devices/printer_a/inc/adapter/rule/Rules.hpp` の
  `-Wmisleading-indentation` 警告(72行目付近)
- `-fno-exceptions -fno-rtti` を現行の `CMakeLists.txt` へ追加
  (`old/` には元々あったが、現行には無い)

**確認方法**: `operator new` 差し替えで 0回/周期 になること。`-Wall -Wextra` 警告ゼロ。

### フェーズ1: 固定容量基盤の統合

- `FixedQueue` を `framework/inc/container/` へ移植
  (現行の `Queue` と用途が重なるなら、どちらかへ寄せる)
- 容量パラメータを `framework/inc/datastore/Config.hpp` へ集約
  (構成変更の `RIMConfig.hpp` に相当するものが現行にもある)

**確認方法**: 既存テストが通ること。

### フェーズ2: Capability 層の型消去への置き換え ← 本命

構成変更から以下を `framework/inc/capability/` へ移植する:

- `CapabilityId.hpp` / `CapabilityConfig.hpp` / `CapabilityPayload.hpp`
- `ICapabilityRule.hpp` / `ICapabilityDiffRule.hpp` / `ICapabilityRuleProvider.hpp`
- `CapabilityStore.hpp` / `CapabilityEvaluator.hpp` / `CapabilityChangeTracker.hpp`
- `CapabilityChangeList.hpp`

現行から削除・移設するもの:

- `framework/inc/capability/CapabilitySet.hpp` の8種(`ErrorCap` / `JobCap` / …)
  → `devices/printer_a/inc/capability/` へ
- `CapabilityKind.hpp` / `CapabilityDiffChecker.hpp` → 型消去側で代替
- `ICapabilityBuilder` → `ICapabilityRuleProvider` へ

**この時点で `framework/` から機種語彙が消える。** これが移行の本丸。

**確認方法**: `grep -rn "ErrorCap\|JobCap\|EnvCap" framework/` が0件になること。

### フェーズ3: core ↔ products の接続を `ProductBinding` 方式へ

構成変更の `ProductBinding.hpp`(宣言だけ core に置き、定義は devices 側で
リンク時解決)を移植する。現行は `RIMSystem` のコンストラクタ引数で注入しているので、
**現行の方式で足りるなら移植しない**判断もあり得る。
`RIMDataId` のヘッダ注入と同じ考え方なので、揃えるなら移植する。

### フェーズ4: Publisher 層(§4.2 の判断後)

### フェーズ5: C API の統合

- 現行 `rim_capi.h` の単位対応・`static_assert` ドリフト検査は残す
- 構成変更 `rim_api.h` の **id 引数方式**(`RIManager_GetCapability` など)を取り込む
  → 現行の `RIManager_GetEnvironment` 系は Capability を増やすたびに API が増えるため
- 試験は現行の3種(smoke / value / perf)を土台にし、型消去の往復と
  バッファ不足の扱いを追加する

### フェーズ6: 後片付け

- `構成変更/` ディレクトリを削除
- `old/` の扱いを決める
- 死んだヘッダ4件は移行しない(そのまま捨てる)

## 6. 移行しないもの

| 対象 | 理由 |
|---|---|
| `core/adapter/` のセンサ別アダプタ13件 | 現行の `IRuleResolver` + テーブル方式が上位互換。うち3件はそもそもコンパイルできない |
| `core/adapter/include/rule/` の空スタブ | `DoorSensorRule.hpp` / `HumiditySensorRule.hpp` は TODO コメントのみ |
| `core/storage/include/RIMDataId.hpp` | 現行では devices 側にある(そちらが正) |
| 実質空のテスト20件 | 82件中20件が3行以下(コメントのみ)。移す価値が無い |
| `ExtendedCapabilityManager` 等 | 既に構成変更側で削除済み |

## 7. 未解決事項(移行と独立)

移行の前後どちらでも良いが、いずれ決着が要るもの。

- **閾値付近のばたつき**。量子化境界で ±0.0006℃ の雑音により
  1000回の配信で999回の状態反転を観測した。ヒステリシス/デバウンスが要る。
- **範囲外・NaN 入力**が未チェック(未定義動作)。
  int32 は 21,474,836 K で溢れる。これは double の精度限界より 4.19M 倍手前。
- **異常構造体リストの要件**(Phase 14)が未決着。
  置き換え(案A)か併存(案B)かを決めていない。
- **gtest が当環境で取得できない**(ネットワーク制限)。
  構成変更ツリーのテストは構文・型検査までしか確認できておらず、
  **アサーションの実行確認は未実施**。移行時に実行環境を用意すること。
