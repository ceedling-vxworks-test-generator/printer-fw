# RIM 移行計画

現行ツリー(`framework/` `devices/` `capi/`)と構成変更ツリー
(`構成変更/librim/RIManager/`)をどう1本にまとめるかの計画。

すべて **実際にビルド・計測して確認した事実** に基づく。推測の箇所はその旨を明記する。

---

## 1. 結論

**構成変更ツリーをベースにし、現行ツリーからは Adapter 層・`RIMDataId` の配置・
install 一式を移植する。**

### 訂正

本書の初版は「現行ツリーをベース」としていた。その後、以下2点が決まったことで
移す量が逆転したため、方針を差し替えた。

- **スレッドモデル: RIM 内で完結**(= 構成変更のワーカ3本方式を採る)
- **Publisher 層: 構成変更側に合わせる**

L2 のスレッドモデルと L3・L4 が構成変更側になると、現行をベースにする場合は
Capability(750行)+ Publisher(813行)+ ワーカ/キュー(153行)に加えて
現行 L2 の作り替えが要る。対して構成変更をベースにするなら Adapter(165行)+
機種規則(約200行)+ `RIMDataId` 移設 + install 一式で済む。

## 2. 層ごとの現状比較

| 層 | 現行 | 構成変更 | 採用 |
|---|---|---|---|
| Adapter (L1) | `RawValue` / `DataContext` / `IRule` / `IRuleResolver`。単位正規化(摂氏・華氏→ケルビン)、テーブル方式ディスパッチ | センサ種別ごとに1クラス。core が機種 id を参照。コンパイルできないヘッダ4件 | **現行** → 移植済み |
| Datastore (L2) | `CentralInputPort` + 3レジストリ(CurrentValue / Fault / Operation)+ `RegistryDomain`。単一スレッド | `ValueStore` + `RIMSnapshot` + ワーカ3本 + キュー | **構成変更**(スレッド方式の決定に従う)<br>3レジストリ構造は §5 フェーズ2 で再検討 |
| Capability (L3) | `CapabilitySet` に8種の Cap を `framework/` へ直書き | `CapabilityId` + `CapabilityPayload`(型消去)、規則は products 側 | **構成変更** |
| Publisher (L4) | `PublishEngine` / `SubscriptionBroker` / `StateRepository` | `SubscriberMailbox` / `CallbackSubscriptionRegistry`(いずれも固定容量) | **構成変更**(決定済み) |
| コンテナ | `FixedMap` / `FixedVector` / `Queue` / `RingBuffer` | `FixedVector` / `FixedQueue` | 構成変更 +(必要なら `FixedMap` / `RingBuffer` を移植) |
| C API | `rim_capi.h` + `rim_ids.h`。単位対応、`static_assert` ドリフト検査、試験3種(smoke/value/perf) | `rim_api.h`(id 引数方式)+ トランポリン枠 | **統合**(単位対応とドリフト検査は移植済み。試験は §5 フェーズ4) |
| ビルド | install / export / pkg-config / find_package | `-fno-exceptions -fno-rtti` | **両方**(install は §5 フェーズ3) |

### 計測値

| 項目 | 現行 | 構成変更(改修前) | 構成変更(改修後) |
|---|---|---|---|
| 定常運転中の動的確保 | 1.0 回/周期 | 3.2 回/周期 | **0 回/周期** |
| 確保箇所 | `CurrentValueBuffer::TakeUpdatedValues()` が `std::vector` を返す 1箇所のみ | Snapshot / ValueStore / キュー3種 / ErrorRepository ほか | なし |

いずれも `operator new` を差し替えて 1000 周期を計測した実測値。

## 3. 構成変更ツリー側で埋めるべき差分

初版で「現行の方が進んでいる」として挙げた点は、**すべて構成変更ツリー側へ移植して
解消済み**(§8 参照)。記録として残す。

### 3.1 構成変更ツリーにあった不足(移植済み)

- **`RIMDataId` が core にある**(`core/storage/include/RIMDataId.hpp`)。
  現行では既に `devices/printer_a/inc/datastore/RIMDataId.hpp` へ移してあり、
  `framework/` は機種固有 id を **一切参照していない**(grep で確認済み)。
  構成変更ツリーはこの点で退行している。

- **Adapter が機種知識を持つ**。`core/adapter/include/CelsiusTemperatureAdapter.hpp`
  などセンサ種別ごとにクラスがあり、`RIMDataId::TemperatureAbsolute` を直接参照する。
  現行はこれを `IRuleResolver` + テーブル方式に置き換え済みで、
  規則が100〜1000件に増えても core は無改修。

- **単位正規化が無い**。構成変更ツリーは「摂氏用アダプタ」「ケルビン用アダプタ」と
  **型で単位を分けている**。現行は `DataContext::unit` で受けて1つの規則が正規化する
  (同じ id に摂氏でも華氏でも入れられる)。これは仕様で決めた振る舞いなので、
  構成変更の形に戻すと要件を満たさなくなる。

- **死んだヘッダが4件ある**。単体でコンパイルできない:
  `CelsiusTemperatureAdapter.hpp` / `HumidityAdapter.hpp` /
  `KelvinTemperatureAdapter.hpp`(存在しない `SensorData.hpp` を include)、
  `products/skeleton/Pipeline/SkeletonProvider.hpp`(相対パス誤り)。
  どの `.cpp` からも include されていないため今まで気付かれていない。

- **install / packaging が無い**。現行にはある(`rim.lib` として mainFW へ
  組み込むために作った export / pkg-config / find_package 一式)。

### 3.2 構成変更ツリーが解決した問題は1層に閉じている

構成変更ツリーの成果は実質2つで、いずれも移植できる:

1. **Capability の型消去**(`CapabilityId` + `CapabilityPayload`)と
   core/products 分離。現行の `CapabilitySet`(8種を `framework/` に直書き)を
   置き換える対象がはっきりしている。
2. **固定容量基盤**(`FixedVector` / `FixedQueue`)と `-fno-exceptions -fno-rtti`。
   現行には既に `FixedMap` / `FixedVector` / `Queue` / `RingBuffer` があるので、
   足りないのは `FixedQueue` と、`CurrentValueBuffer` の1箇所の修正だけ。

### 3.3 作業量の見積り(判断後)

| 方向 | 移す対象 | 概算 |
|---|---|---|
| 構成変更 ← 現行(採用) | Adapter(165行)+ 機種規則(約200行)+ `RIMDataId` 移設 + install 一式 | 約450行 |
| 現行 ← 構成変更 | Capability(750行)+ Publisher(813行)+ ワーカ/キュー(153行)+ 現行 L2 の作り替え | 1,700行超 |

## 4. 決定済みの事項

### 4.1 スレッドモデル: **RIM 内で完結**(決定済み)

構成変更のワーカ3本(`DataStoreWorker` / `CapabilityWorker` / `PublisherWorker`)を
採る。呼び出し側(mainFW)は `RIManager_Start()` を呼ぶだけでよく、
タスクの起動・停止は RIM が持つ。

現行の「呼び出し側が `Dispatch()` を回す」方式は採らない。

### 4.2 Publisher 層: **構成変更側**(決定済み)

`SubscriberMailbox` / `CallbackSubscriptionRegistry` / `ChangeNotifyManager` を採る。
現行の `PublishEngine` / `SubscriptionBroker` / `StateRepository` は移行しない。

## 5. 段階

各フェーズは **単独でビルドが通り、単独でマージできる** 単位に切ってある。
途中で止めても壊れた状態にはならない。

### フェーズ1: Adapter 層の移植 — **完了**(§8)

### フェーズ2: Datastore 層の残差

構成変更の L2 は `ValueStore` 1本だが、現行は入力の性質ごとに
3レジストリ(CurrentValue / Fault / Operation)へ振り分けている。
現状の `QueueInputPort` は単一レーンへ集約しており、**この振り分けは未移植**。

- `IInputClassifier` 相当(id → 入力性質)を products 側へ
- `FaultRegistry` / `OperationRegistry` / `RegistryDomain` を移植するか、
  Capability 規則側で吸収するかを決める
- 現行の `FixedMap` / `RingBuffer` が要るならここで移植

**判断が要る**: 3レジストリ構造を残すか、`ValueStore` 1本のままにするか。
仕様(§6.2/§6.3 の性質別入力レーン)に紐づくため、要件確認が必要。

### フェーズ3: install / packaging の移植

現行の `rim.lib` 一式(install / export / pkg-config / find_package)を
構成変更ツリーへ持ち込む。`RIMDataId.hpp` が products 側に移ったので、
install 後の include レイアウトを合わせ直すこと。

**確認方法**: 外部の消費側プロジェクトから `find_package` して実際にリンクできること。

### フェーズ4: C API 試験の移植

現行の smoke / value / perf(C から実際にリンクして実行する試験)を移植する。
型消去 API 向けに、往復の一致とバッファ不足の扱いを加える。

### フェーズ5: 後片付け

- `構成変更/librim/RIManager/` をリポジトリ直下へ移す
- 旧 `framework/` `devices/` `capi/` を削除
- `old/` の扱いを決める
- 実質空のテスト20件を整理する(82件中20件が3行以下)

## 7. 未解決事項(移行と独立)

移行の前後どちらでも良いが、いずれ決着が要るもの。

- **閾値付近のばたつき**。量子化境界で ±0.0006℃ の雑音により
  1000回の配信で999回の状態反転を観測した。ヒステリシス/デバウンスが要る。
- **範囲外・NaN 入力**が未チェック(未定義動作)。
  int32 は 21,474,836 K で溢れる。これは double の精度限界より 4.19M 倍手前。
- **異常構造体リストの要件**(Phase 14)が未決着。
  置き換え(案A)か併存(案B)かを決めていない。
- **gtest が当環境で取得できない**(ネットワーク制限)。
  構成変更ツリーのテストは構文・型検査までしか確認できておらず、
  **アサーションの実行確認は未実施**。移行時に実行環境を用意すること。

## 8. 実施済み(フェーズ1)

構成変更ツリーへ以下を移植し、動作を確認した。

### 移植したもの

| 内容 | 移送先 |
|---|---|
| `RawValue`(スカラ/構造体/配列を非所有参照で受ける) | `core/adapter/include/` |
| `IRule` / `IRuleResolver` / `RawDataInput`(受理点1本) | `core/adapter/include/` |
| `DataContext` / `SourceUnit` / `FaultState` / `RIMResult` | `core/storage/include/` |
| `ICentralInputPort` + `QueueInputPort`(キューへの実装) | `core/storage/` `core/store/` |
| PrinterA の正規化規則(温度・百分率・真偽・計数) | `products/printer_a/DataItem/PrinterARules.hpp` |
| id → 規則のテーブル(`static_assert` 付き) | `products/printer_a/DataItem/PrinterADataProfile.*` |

### 構造の変更

- **`RIMDataId` を core から products へ移した**。core は
  `#include "RIMDataId.hpp"` と名前だけで書き、実体は機種側が供給する。
  core 単体ではビルドが通らないことを実際に確認済み(意図した失敗)。
  番兵 `kCount` と `ToIndex()` は現行ツリーから取り込んだ。
- **`RIManager_Push(id, value, ctx)` を C API に追加**した。
  従来の `RIManager_TestInject*` はキューへ直接積んでおり、
  **規則による正規化を素通り**していた。現在はどちらも Adapter 経由。
- **core → products の include を排除**。規則表の取得も `ProductBinding` の
  `GetProductRuleResolver()` を経由し、リンク時解決にした。
- `PrinterAdapter` は `RIMDataId::kTemperatureSensorA` を直接使うため
  core から products へ移した。

### 削除したもの

- センサ種別ごとのアダプタ8件、空の規則スタブ6件、`AdapterFactory`
- それらを対象にしていた試験4件(新しい Adapter 層の試験に差し替え)

### 追加した試験

`RawDataInputTest`(規則適用・未知 id・変換失敗・context の運搬)、
`RawValueTest`(構造体/配列を**コピーせず参照する**こと)、
`PrinterARulesTest`(摂氏・華氏・未指定、スケール、クランプ)、
`PrinterADataProfileTest`(全 id が規則に対応し、表の並びが崩れていないこと)。

### 副次的に見つけて直したもの

- `products/skeleton/` の雛形が **PrinterA の id を参照していた**。
  そのままでは新機種を起こせないため、skeleton 自身の id へ直し、
  `RIMDataId.hpp` / `SkeletonDataProfile.*` の雛形を追加した。

### 検証

- 全103ソースを `-Wall -Wextra` で警告ゼロ
- `-fno-exceptions -fno-rtti` でライブラリをビルドし、**C から実際にリンクして実行**
  - 摂氏25.0 → 298.150000 K
  - 華氏77.0 → 298.150000 K
  - **差分 0.000000000000**(単位に依らず同じ状態になる)
  - 単位未指定300.0 → 300.000000 K(換算しない)
  - 未知 id → `RI_INVALID_PARAMETER`
- 定常運転中の動的確保 **0回/周期**(Adapter 経由に変えた後も維持)
